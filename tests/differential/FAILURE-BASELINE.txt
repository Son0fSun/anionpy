# +2 names: `longdouble_list_ctor`/`clongdouble_list_ctor` -- NOT
# `longdouble`/`clongdouble` themselves (those are added to scalar_cases.py
# and pass fully, 23/23 and 15/15 cases). These two are a narrow,
# disclosed, deliberately-separated edge case this ticket's own tests
# found while adding `anionpy.longdouble`/`anionpy.clongdouble`:
# `anionpy.longdouble([1, 2])`/`anionpy.clongdouble([1, 2])` build an array
# that matches real numpy on value/dtype.name/itemsize but not on
# `repr()` -- real numpy's array repr prints an explicit
# `", dtype=float64)"`/`", dtype=complex128)"` suffix for an array sourced
# from `np.longdouble`/`np.clongdouble` (its dtype is the distinct
# `'g'`/`'G'`-spelled one, not the plain default `'d'`/`'D'` one repr
# compares against), while anionpy's array-building compat shim
# (`build_array_for_dtype` in scalars.rs) has no way to tag an array with
# that spelling -- `NdArray`/`PyArray` carry a bare `DType` enum, no
# per-instance spelling tag at all (only `PyDType`, the scalar dtype
# object, has one, from ticket #78). Giving arrays that same tag would be
# the same out-of-scope "route dtype identity through a class/tag table
# instead of a bare enum, project-wide" change already declined for the
# `dtype('g')`-not-becoming-`LongDoubleDType` gap (see
# `ionp-py/src/dtypes_module.rs`'s doc comment). Neither name is in
# `tools/numpy_surface.json` (not a manifest surface item), so this can
# never gate/phantom the ticket's actual 4 declared items
# (`longdouble`/`clongdouble`/`dtypes.LongDoubleDType`/
# `dtypes.CLongDoubleDType`, all declared "exact" in
# `anionpy/_state/scalars.py`) -- kept here, visible and failing, so the
# gap is not silently dropped.
