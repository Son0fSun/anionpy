**Splitting the "matrix/memmap/recarray/chararray don't exist" line:** the honest
framing is two layers, not one flat 714:
1. **Layer A (LARGE, ~100-150 items of real new logic):** finish the `ndarray`
   core surface — buffer protocol, `__dlpack__`, `__array_interface__`/`__array_struct__`,
   `__array_ufunc__`/`__array_function__` dispatch, `view`, `resize`, `put`,
   `partition`/`argpartition`, `dot`, `ctypes`, `flat`, `getfield`/`setfield`/`setflags`,
   `byteswap`, `device`/`to_device`. This is the genuine remaining ndarray wall (33
   items) and it recurs identically inside matrix/memmap/recarray/chararray by
   inheritance (verified: matrix's absent-list is a strict superset of ndarray's).
2. **Layer B (MEDIUM, subclass boilerplate):** once Layer A exists, standing up
   `matrix`/`memmap`/`recarray` as thin `ndarray` subclasses is mostly `__new__`/
   `__array_finalize__` plumbing plus a handful of genuinely subclass-specific
   methods (matrix's `getH`/`getI`/`A`/`A1`/`H`/`I`/`getT`; recarray's `field`;
   memmap's `flush`+mmap-backed storage, which is its own small OS-level piece).
   `char.chararray` is different in kind — it needs the string-dtype subsystem
   (Layer above), not just ndarray subclassing, because chararray IS the
   string-array type.

## 3. Free wins — items that already resolve on the live binary

**Method:** exhaustive `getattr`-chain probe of all 2198 absent dotted paths against
a live `import ionp` session (from neutral `/private/tmp` cwd, confirming the
installed package, not repo source). This is a full-population check, not a
sample — every one of the 2198 names was resolved or not. Where a group's items
are per-class members (e.g. `random.Generator.beta`), resolution was checked via
`hasattr` on the class/instance, same as `coverage.py`'s own resolution logic

**Explicit caveat, per the task brief: a working `getattr`/`hasattr` result is
evidence of EXISTENCE, not CORRECTNESS.** Declaring any of these requires the
differential corpus. Two sub-categories below matter differently:

- **"dunder-present" (155 items):** trivially resolve because they're inherited
  from `object` (`__eq__`, `__format__`, `__dir__`, `__reduce__`, …) on classes
  like `finfo`/`iinfo`/`dtype`/`random.Generator`/`polynomial.*`. These almost
  certainly do NOT implement numpy-shaped semantics (`object.__eq__` is identity
  comparison, not numpy's). **Do not count these as free wins** — they are noise
  in the raw resolve-count, called out separately so nobody mistakes 155 dunders
  for 155 hours saved.
- **"real-present" (144 items):** non-dunder names that resolve. These are the
  actual candidates — functions/methods that appear to exist and, in every case
  spot-checked with an actual call (not just `hasattr`), produced numpy-shaped
  output.

## 4. Effort ranking and execution order

### SMALL (days, largely declare-and-test on top of what exists)
- **`fft`** (13 items, 12 already resolve) — spot-check values against numpy,
  write differential tests, declare. Fastest points on the board.
- **`linalg`** (11 items, 10 already resolve) — same shape as fft.
- **`exceptions`** (7 items) — plain Python exception/warning classes, no numeric
  logic.
- **`emath`, `testing`** (4 items combined) — thin wrappers.
- **RNG core declare-and-test** (the ~47 real-present `random.Generator` +
  `ma`-adjacent items, i.e. the 20 bit-exact continuous distributions plus PCG64/
  PCG64DXSM themselves) — MEASURED bit-exact, this is pure paperwork (differential
  corpus + declaration), not implementation.

### MEDIUM (1-3 weeks each)
- **toplevel free-standing gap** (127 genuinely absent of 171) — a grab-bag;
  many are wrappers around existing ndarray ops (`apply_along_axis`, `block`,
  `bincount`, `argpartition`) blocked mostly by the ndarray Layer-A gap above
  (`argpartition`, `put`-based things) rather than needing new numerics.
- **`dtype`/`finfo`/`iinfo`/`dtypes` core** (52+33+28+34 = 147, minus the 24+25+25
  dunder-noise) — mostly real work is in `dtypes.*` (34 DType metaclass exposures,
  0 present) and the ~26 non-dunder `finfo`/`iinfo` numeric properties; the
  dunder counts are inflated by `object`-inherited noise as shown in Part 3.
- **7 missing `Generator` distributions + array-shaped RNG ops** (`poisson`,
  `triangular`, `vonmises`, `wald`, `zipf`, `geometric`, `logseries`,
  `multivariate_normal`/`multinomial`/`dirichlet`/`choice`/`shuffle`/`permutation`)
  — real numerics, but narrow and well-precedented (numpy's C source is the spec).
- **matrix/memmap/recarray Layer B** (subclass boilerplate, contingent on Layer A
  landing first) — see Part 2 split.
- **`poly1d`** (53 items, class doesn't exist) — much smaller and simpler than the
  `polynomial.*` ABCPolyBase family; legacy single-variable polynomial with a
  flat coefficient array, no per-basis dispatch.
- **`rec`, `ctypeslib`, `lib`** (17 items combined) — thin, but `ctypeslib` is
  gated by the ndarray buffer/ctypes gap in Layer A, so it can't fully land before
  that does.

### LARGE (genuinely multi-week, name it plainly)
- **`ndarray` Layer A core surface** (33 items, but the highest-leverage 33 in
  the whole map since matrix/memmap/recarray/chararray all inherit the same gap).
  Buffer protocol + `__array_interface__`/`__array_struct__`/`__dlpack__` +
  `__array_ufunc__`/`__array_function__` dispatch are genuine, fiddly systems
  work, not routine ports. **This is months, not weeks, if done to the standard
  the rest of ionp holds itself to (bit-exact, not "close").**
- **String dtype subsystem** (232 direct items in char/strings, plus it's a
  prerequisite for chararray's 204-item share of the matrix-family gap, plus an
  unmeasured number of comparison ufuncs per the task brief's own finding today).
  This is a new dtype kind end-to-end: storage representation, casting rules,
  ufunc registration, `dtype()` string parsing, printing. **Multi-week, likely
  the single largest true engineering lift in this map alongside Layer A.**
- **`polynomial.*` family** (453 items). Real effort is smaller than 453 implies
  because the 6 classes share ~98% of their method surface (measured: only
  `interpolate` differs between Chebyshev and Polynomial) — a single generic
  `ABCPolyBase`-equivalent plus 6 sets of basis-specific primitives (`vander`,
  companion-matrix, `fromroots`) does most of the job. But `fromroots`/`roots`
  need eigenvalue solving, and **`linalg.eig` was not found in the probed
  linalg absent/present lists at all** — worth an explicit follow-up check
  before scoping this, since a missing general eigensolver would silently
  block `roots()` for every one of the 6 classes at once. Call this **LARGE**,
  multi-week, until eig support is confirmed.
- **`ma` real remaining work** (301 - 36 - 26 = 239 genuinely absent, and per
  the corrected finding in Part 2, `MaskedArray` itself is only ~24% built, not
  ~98% as a prior note claimed). Once the ndarray Layer A dunders exist,
  `MaskedArray`'s own arithmetic dunders (`__add__`, `__getitem__`, etc.) still
  need mask-propagation semantics layered on top — not a copy-paste of ndarray's,
  a systematic wrapper over ~50 dunders/ufuncs. **MEDIUM-LARGE**, larger than
  previously assumed.
- **`matrix`/`memmap`/`recarray`/`char.chararray` Layer A dependency**: already
  captured above; flagged again here because their total item count (714) makes
  them look like the biggest single group in a naive reading, when the real
  gate is the 33-item ndarray core plus (for chararray) the string-dtype system.
  Once those two land, Layer B for all four is MEDIUM, not LARGE.
- **Legacy RNG (`RandomState`, `MT19937`, `Philox`, `SFC64`)** — 74 items, and
  unlike the Generator/PCG64 stack, **zero evidence these exist yet**
  (`hasattr(ionp.random, 'MT19937')` etc. all `False`). This is real,
  independent bit-generator + legacy-API work, not covered by the PCG64 win.
  MEDIUM-LARGE.
- **datetime64/timedelta64** — narrow item count but calendar arithmetic
  (`busday_count`/`busday_offset`/`busdaycalendar`) is fiddly correctness work
  disproportionate to its ~10-item footprint. MEDIUM, called out here because
  it's easy to underestimate from the count alone.

### Recommended execution order (items-per-unit-effort, descending)
1. **Declare-and-test sweep of the 144 real-present items** (Part 3) — SMALL,
   highest points-per-hour on the board, contingent only on building the
   differential corpus and confirming actual correctness (not just existence).
   Start with the 20 bit-exact RNG distributions and the fft/linalg near-complete
   groups — those already have a working oracle to diff against (numpy itself,
   same seed).
2. **`ndarray` Layer A core surface** — LARGE but do it early anyway, because it
   is the load-bearing dependency for ~250+ downstream items across
   matrix/memmap/recarray/toplevel. Delaying it means re-discovering the same
   gate under four different group names later.
3. **`poly1d`** — MEDIUM, self-contained, no dependency on Layer A or string
   dtype, good parallel track while Layer A is in progress.
4. **Legacy RNG (`MT19937`/`RandomState`)** — MEDIUM-LARGE, self-contained,
   parallelizable with Layer A since it doesn't touch ndarray internals.
5. **`matrix`/`memmap`/`recarray` Layer B** — once Layer A lands, this is fast;
   sequence it right after.
6. **`polynomial.*` family** — LARGE, start once Layer A's `dot`/eigen-adjacent
   pieces are confirmed and after resolving the open `linalg.eig` question above.
7. **`ma` real remaining 239** — MEDIUM-LARGE, sequence after Layer A since
   MaskedArray dunders build on ndarray dunders.
8. **String dtype subsystem** — LARGE, the other genuinely multi-week item;
   start in parallel with Layer A if there is a second engineering track
   available, since neither blocks the other and both unblock large downstream
   groups (char/strings/chararray for strings; matrix/memmap/recarray/toplevel
   for Layer A).
9. **datetime64/timedelta64, dtypes.* metaclasses, ctypeslib, rec, lib,
   exceptions** — mop-up, MEDIUM/SMALL, fill gaps between the above.

**Groups that are genuinely months, stated plainly:** `ndarray` Layer A (buffer/
dlpack/array-protocol dispatch), the string dtype subsystem, and — pending the
`linalg.eig` check — `polynomial.*`. Everything else in this map is weeks or
less once its stated dependency is in place.

## Independent verification by Monday, 2026-08-06

Two claims in this map change the project schedule, so both were re-measured
directly rather than accepted.

### 1. `random.Generator` bit-exactness — CONFIRMED, and it resizes the plan

The approved plan calls `random` "the genuine multi-week wall" and budgets a
bit-exact rewrite of PCG64, MT19937, Philox and SFC64 in Rust.

Measured: **32/32 bit-exact, 0 mismatched, 0 errored** — 4 seeds
(`0`, `1`, `12345`, `2**63+7`) x 8 distributions (`random`,
`standard_normal`, `exponential`, `gamma`, `beta`, `chisquare`, `uniform`,
`normal`), `size=7`, compared with `np.array_equal` against
`np.random.Generator(np.random.PCG64(seed))`.

The plan's own instruction was to *"start by measuring how close that is to
numpy's stream rather than assuming a rewrite."* That measurement is now done
and the answer is: for PCG64 + these distributions, **the stream already
matches**. The remaining `random` work is declaration, corpus and the
*other* bit generators — not a from-scratch PCG64.

**ILLUSTRATIVE, NOT EXHAUSTIVE.** PCG64 only — MT19937, Philox and SFC64 were
NOT tested. 8 of 27 distributions. One size. No `RandomState` legacy API. No
discrete distributions. No `out=`/`dtype=`/`axis=`. No jumped/advanced
streams. Bit-exactness on these 32 draws is not bit-exactness on the
generator surface, and nothing here is declarable without a corpus.

### 2. `ma` is FAR less complete than stored project memory says — memory FALSIFIED

Stored memory, carried into the approved plan: *"MaskedArray is just an
ordinary data+mask array pair, and only 5 of 225 items need in-place writes."*
That framing made `ma` look tractable and ranked it 4th in the Phase 4 order.

Measured against the live binary:

```
>>> ionp.ma.array([1,2,3], mask=[0,1,0])
AttributeError: module 'ionp.ma' has no attribute 'array'
```

**`ionp.ma.array` does not exist at all.** The constructor is missing, so the
"only 5 items need work" note cannot be evaluated on its own terms — this
audit's separate finding of 146/191 `MaskedArray` members absent (including
`__getitem__`, `__add__`, `T`, `__array__`) is consistent with that.

**The old note is falsified and must not be used for planning.** Anyone
sequencing `ma` work should re-derive its scope from the current binary. This
is the third time this week a recorded reason in the repo turned out not to
describe the shipped code.

**Not checked here:** whether some other constructor spelling exists
(`ionp.ma.MaskedArray(...)`, `masked_array`), which would change the shape but
not the conclusion that the stored note is unreliable. One probe, one spelling.

# CORRECTION, 2026-08-06 — the `linalg.eig` claim in this document is FALSIFIED

This document states that `linalg.eig` "was not found in the probed linalg
absent/present lists at all" and warns that "a missing general eigensolver
would silently block `roots()`."

**Measured directly against the installed `.so`, from `/private/tmp`:**

```
linalg.eig       present=True
linalg.eigvals   present=True
linalg.lstsq     present=True
linalg.pinv      present=True
linalg.svd       present=True
linalg.qr        present=True

>>> c = ionp.array([[0.,0.,-6.],[1.,0.,11.],[0.,1.,-6.]])   # non-symmetric companion
>>> ionp.linalg.eigvals(c)
[ 0.78000275+0.43040205j  0.78000275-0.43040205j -7.56000551+0.j]
>>> np.linalg.eigvals(<same>)
[ 0.78000275+0.43040205j  0.78000275-0.43040205j -7.56000551+0.j]
```

Identical, on the general non-symmetric case a companion matrix actually
produces — not the easier Hermitian path. `linalg.eig`/`eigvals`/`lstsq` are
implemented (`ionp-py/src/linalg.rs`), registered, and declared `"exact"` in
`ionp/_state/linalg.py`. Added in commit `40c0c7e`.

**Consequence:** the two dependencies repeatedly named as the hard blockers
for the polynomial subsystem — `*fit` (least squares) and `*roots`
(companion-matrix eigenvalues) — are **not blocked**. Polynomial is cheaper
than this document priced it.

The genuinely absent primitives are different ones, measured the same way:
`convolve`, `correlate`, `vander`, `poly1d`, `polyval`, `polyfit`, `roots`,
and `ionp.polynomial` itself — all `present=False`. Per-basis multiplication
(Chebyshev product-to-sum, Legendre recurrence) is real numerical work and is
NOT simple convolution; that, not the eigensolver, is the remaining wall.

**Why this correction exists rather than a silent edit:** this is the fifth
time this week a recorded reason in this repo failed to survive measurement
(the others: the `UFuncTypeError` design note's "not started", the stored `ma`
tractability note, the `order='K'`/Finding-D mislabel, and `_dtypeinfo.py`'s
"ionp has no scalar type classes yet"). The original text stays visible above.
A claim I could not reproduce is not the same as a claim I disproved — this
one I disproved, and the repro is pasted so anyone re-opening it can run it.

The rest of this document has NOT been re-verified. One falsified claim in it
is grounds to treat the others as claims, not facts.
