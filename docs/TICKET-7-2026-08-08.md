# Ticket #7 — 2026-08-08

Fixes the ufunc output-allocation `order='K'` path losing/mangling F-order
stride layout specifically when an operand has a length-1 axis. Two
committed Rust source edits, one committed differential-test edit, one
Rust regression-test addition. No Python source touched.

**Commit measured against (starting point): `2d8089d`** (working tree
clean before this pass's edits).

## 1. The code path (and: does `sort` share it?)

`ndarray.__abs__`/`np.abs`/every other unary and binary ufunc's plain
`__call__` routes to `apply_ufunc_order` in `ionp-py/src/lib.rs`. Its
`'K'` (keep) arm decides the output's memory layout. Before this fix it
called `NdArray::multi_sorted_stride_perm` (`ionp-core/src/array.rs`)
directly on every call.

`sort` does **not** share this helper. `sort.rs` hardcodes
`ArrOrder::C` for its output regardless of input layout — a different,
already-out-of-scope-for-#7 defect (belongs to #64), confirmed by reading
`sort.rs` directly: there is no call from there into
`apply_ufunc_order`/`multi_sorted_stride_perm` anywhere in the crate.
`grep -rn "multi_sorted_stride_perm\|apply_ufunc_order" ionp-py/src
ionp-core/src` shows exactly one call site of each, both inside
`apply_ufunc_order` itself. `sort` failing on the same repro shapes is
coincidence of symptom (both happen to be wrong about F-order strides at
a size-1 axis), not shared cause.

## 2. The two bugs and the fix

### Bug A — `multi_sorted_stride_perm`'s scan

The port of numpy's `PyArray_CreateMultiSortedStridePerm` (`shape.c`)
had two defects:

1. It `break`-ed out of the axis-pair scan on the first AMBIGUOUS
   comparison (an operand where one of the two compared axes has size 1)
   instead of continuing to scan further back for a later, DECISIVE
   comparison. numpy's real algorithm keeps scanning past ambiguous
   comparisons.
2. Its insertion was incremental (mutating the permutation mid-scan)
   instead of numpy's real two-phase design: track the final insertion
   position (`ipos`) across the whole backward scan without mutating,
   then do one bulk shift.

Fixed by porting the real algorithm exactly (see the function's own doc
comment in `ionp-core/src/array.rs`, ~line 1116).

### Bug B — single/whole-agreeing-operand fast path

Even with Bug A fixed, `multi_sorted_stride_perm` alone still cannot
correctly decide a SINGLE operand whose whole-array contiguity is
genuinely, wholly F — e.g. `zeros((4,1,2)).copy('F')`, which real numpy
reports `F_CONTIGUOUS=True` for (strides `(8,32,32)` bytes) despite the
interior size-1 axis. Every per-axis-pair comparison that touches the
size-1 axis is ambiguous by definition (a size-1 axis is walked once
regardless of its stride, so no comparison touching it can ever be
decisive), so no per-axis algorithm alone can recover the answer.

Real numpy resolves this at a higher level first: a whole-array flags
check. `apply_ufunc_order`'s `'K'` arm now requires **ALL** operands to
agree on whole-array C-contiguity (or ALL agree on F-contiguity) before
taking an identity/reversed fast path; only when operands genuinely
disagree (or none is wholly C/F) does it fall through to the general
per-axis algorithm.

**"All operands agree" is required, not "first operand wins."** An
earlier attempt (previous session, same ticket) used
`k_order_relayout_composed`'s "first C-or-F operand wins outright" rule
here. That is order-DEPENDENT: verified live against real numpy that two
genuinely-conflicting C/F operands always resolve to C order regardless
of argument order (`np.add(c, f)` and `np.add(f, c)` both give the same
C-order result) — a "first wins" rule instead gives whichever operand
happened to be checked first, which is wrong whenever the caller passes
the F operand first. That earlier attempt measured a 42-item regression
across `order/ufunc/*` before being abandoned in favor of the
all-agree/fall-through design in this fix.

## 4. The `add-broadcast-0d` 30-case finding — not a defect

`/private/tmp/ticket7_corpus.py` (a purpose-built differential corpus,
written before declaring the fix done, covering 5 dtypes × 22 shapes ×
5 layouts × {abs, negative, invert, add-broadcast-0d}, 1616 total checks)
found 30 remaining stride-value mismatches, all in `add-broadcast-0d` on
float32/int32/bool_ operands with a size-1 axis under `'F'`/`'transposed'`
layout, all AFTER dtype promotion (e.g. `np.add(float32_array, np.array(2))`
promotes to float64).

Investigated directly against real numpy: even numpy's OWN freshly
dtype-promoted allocation produces a non-canonical F stride VALUE at the
size-1 axis position (e.g. `(8,64,32)` instead of the "textbook"
`(8,32,32)`) while still reporting `F_CONTIGUOUS=True` on both sides.
`.flags` agreed in all 30 cases (no `FLAGS`-suffixed failure entries).
Conclusion: this is real numpy's own implementation-defined, unobservable
stride value at a size-1 axis for a freshly-promoted-dtype allocation —
not a correctness defect in anionpy, and not part of the 118-item #7
population (none of the 118 named items are `add`/binary-broadcast
specifically probed this way).

## 5. Regression guard — and why the committed Python differential suite cannot be one

`tests/differential/ufunc_order_cases.py`'s `SHAPES` gained `(4, 1, 2)`
— the ticket's headline repro shape — adding real coverage at every
non-masked axis position across this file's full `order/ufunc/*` matrix.

**This addition is NOT, by itself, a working regression guard for
ticket #7's defect**, and an earlier draft of this file's comment
incorrectly claimed it was ("proven to bite") without having actually
run the revert-and-measure step to completion. Corrected in place, and
proven properly: `tests/differential/harness.py::_strides_match`
deliberately masks stride comparisons at any axis position whose extent
is `<= 1` (documented there as "CLASS B" divergence, added 2026-08-04)
— and all three of this ticket's own repro shapes diverge EXACTLY at
that masked position. Measured directly: reverting
`apply_ufunc_order`'s `'K'` arm to its pre-fix form, rebuilding, and
rerunning the full differential suite with `(4,1,2)` present in `SHAPES`
reproduces the identical 29-item baseline failure set, byte-for-byte,
with zero new failures. The Python suite is structurally blind to this
entire defect class.

**The actual, proven-to-bite regression guard** is a new set of Rust
`#[test]`s added to `ionp-core/src/array.rs`'s existing `mod tests`
block:

- `k_order_unary_f_contiguous_len1_middle_axis` — `(4,1,2)`
- `k_order_unary_f_contiguous_len1_first_axis` — `(1,4,2)`
- `k_order_unary_f_contiguous_len1_last_axis` — `(4,2,1)`
- `k_order_unary_f_contiguous_no_len1_axis_unaffected` — `(4,2)`,
  `(3,4)`, `(2,3,4)` (the three shapes that already passed pre-fix; guards
  against the fix regressing the plain case)
- `k_order_binary_c_f_conflict_resolves_to_c_order_independent` —
  proves conflict resolution is order-independent (both `[c,f]` and
  `[f,c]` argument order give the identical result, and it is C order)

Each test reads `.strides()` directly off the `NdArray` under test
(element-strides, not bytes — `NdArray`'s convention throughout, matches
the file's existing `transpose_reverses_shape_and_strides` test) and
asserts against the ticket's own measured real-numpy repro table
(converted from bytes to elements for `f64`, itemsize 8: `(8,32,32)` →
`(1,4,4)`, `(8,8,32)` → `(1,1,4)`, `(8,32,64)` → `(1,4,8)`).

**Proven to bite**: with the test module's `k_order_perm` helper's
fast-path temporarily deleted (leaving only the corrected
`multi_sorted_stride_perm` call — i.e. simulating Bug B being
un-fixed), all three length-1-axis tests FAIL:

```
k_order_unary_f_contiguous_len1_middle_axis: left [1,1,4] right [1,4,4]
k_order_unary_f_contiguous_len1_first_axis:  left [8,1,4] right [1,1,4]
k_order_unary_f_contiguous_len1_last_axis:   left [1,4,1] right [1,4,8]
```

while the no-len1-axis and c/f-conflict tests still pass (as expected —
their answers don't depend on the fast path the same way). File restored
byte-identical afterward, confirmed via `diff` against the pre-edit
backup (`/tmp/array.rs.testfix.bak`), and the full test module re-run
green (`cargo test -p ionp-core --lib array::tests::k_order`, 5/5 pass).

**Disclosed limitation**: Bug A (`multi_sorted_stride_perm`'s
scan/insertion algorithm itself) is exercised by the binary conflict test
above via its `else` branch, and was independently verified against real
numpy multiple times during investigation (C/F conflict cases at shapes
`(4,1,2)` and `(2,3)`), but there is no dedicated multi-operand
ambiguous-axis-pair Rust test isolating Bug A the way the length-1-axis
tests isolate Bug B. Not claimed as independently guarded.
