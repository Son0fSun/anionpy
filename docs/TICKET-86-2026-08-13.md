# TICKET-86: measure the corpus/comparator blindness, don't fix it -- 2026-08-13

## Scope and rule

This ticket **measures**. It does not repair the code it exposes. #84, #85,
and #87 each found a declared-`exact` item that was actually wrong in the
same family of way (a signed-zero or denormal defect that no test could see
because nothing in the corpus produced the property, or the comparator
couldn't see it even when the corpus did), and each was fixed as a one-off
instance. This ticket's job was to find the CAUSE -- in the measuring
apparatus, not in any one item's code -- close what could legitimately be
closed at the harness/corpus level, and file everything the widened
measurement newly exposes as its own future ticket, without touching the
underlying (buggy) production code.

Repo HEAD at measurement time: `03d2c06`. No Rust changed
(`cargo build -p ionp-py --release` succeeds unmodified from before this
ticket). All edits are in `tests/differential/harness.py`,
`tests/differential/corpus.py`, `tests/differential/ndarray_float_cases.py`,
and this doc + `FAILURE-BASELINE.txt`.

## Step 1: proving the two blindness mechanisms before touching anything

### Mechanism A -- was claimed: "the corpus generators never emit denormals"

**Measured FALSE for `unary_corpus()`, TRUE for `binary_corpus()` and
`scalar_operands()`.** `corpus.py`'s `_special_float_values()` already
contained a `special/denormal/<dtype>` case per float dtype (smallest
subnormal, `np.nextafter(0, 1)`) before this ticket -- confirmed by
measuring `min(|x| for x in unary_corpus() if x != 0)` directly:

```
unary_corpus min nonzero |x| = 5e-324   (== np.finfo(float64).smallest_subnormal)
```

But `binary_corpus()` (used by every binary-op/broadcasting item, and by
every `ufunc.outer()` sampled pool) and `scalar_operands()` (used for the
scalar right-hand-operand call-form axis) had **no** denormal coverage at
all -- every value in both comes from `rng.standard_normal() * 10` or fixed
literals well away from zero:

```
binary_corpus min nonzero |x|  (before) = 0.02
scalar_operands: no denormal entry at all (before)
```

So the premise was real, but scoped more narrowly than stated: the
generator that DIRECTLY feeds every unary item was already fixed by an
earlier ticket; the generators that feed every BINARY item and the
scalar-operand call-form axis were not, and a binary op run
element-by-element against a denormal on one side and a normal value on
the other is a genuinely different code path from either side alone.

### Mechanism A' -- signed zero, same split

Same pattern: `unary_corpus()` already had 8 cases containing `-0.0`
(`special/scalar_neg_zero/<dtype>`, `special/finite_nan_inf/<dtype>`,
`special/complex_nan_inf/<dtype>`). `binary_corpus()` had **zero** pairs
containing a signed zero on either side; `scalar_operands()` had zero
signed-zero entries.

### Mechanism B -- "the comparison path reaches `np.array_equal`, which
IGNORES the sign of zero and dtype"

**Measured PARTLY FALSE, and the true remaining gap is more specific and
more interesting than the premise.** The main array-vs-array comparison
path (`harness.compare_values` -> `_bit_exact_equal`) already does true
byte-level (`tobytes()`) comparison for every float/complex ndarray result,
and dtype is checked (`np_dtype != ionp_dtype`) before any value comparison
is attempted at all -- both closed by an earlier ticket (2026-08-01, per
the in-file docstrings). Direct check:

```python
>>> harness.compare_values(np.array(-0.0), np.array(0.0), None, None)
(False, 'no tolerance declared ... FAILED', False, 0.0)   # correctly rejects
```

The REAL, still-open gap was `harness._compare_scalar_like` -- the
comparison path used whenever `ItemSpec.scalar_like=True` (results that
are NOT ndarrays: `.shape`, `.item()`, `float(arr)`, `.ndim`, etc; roughly
30 case files opt into it). Its plain-`float`/`int` branch fell through to
a bare `x == y`, which IEEE 754 defines as `0.0 == -0.0 -> True` --
structurally blind to sign of zero, by construction. Proven directly, not
hypothetically, against the real function before this ticket's fix:

```python
>>> harness._compare_scalar_like(-0.0, 0.0)
(True, '')          # WRONG: reports these as equal
>>> harness._compare_scalar_like(1.0, 2.0)
(False, 'value mismatch: numpy=1.0 anionpy=2.0')   # sanity: NOT vacuous --
                                                    # real mismatches were caught
```

This was not a guess -- the code's own comment block (directly above the
`complex` branch that WAS already fixed for this exact property) said so
explicitly: *"The float branch above remains `==`-based and so remains
blind to signed zeros; that is pre-existing and is recorded here rather
than changed under cover of an unrelated fix, since tightening it would
re-grade already-passing items and deserves its own measurement."* This
ticket is that measurement.

Also confirmed, per the brief's warned instrument traps, both real:

```python
>>> -0.0+0j
0j                              # sign silently lost; must spell complex(-0.0, 0.0)
>>> np.signbit(np.nan_to_num(np.array(-0.0)))
True                             # nan_to_num PRESERVES -0.0, does not neutralize it
>>> np.array_equal(np.array(-0.0), np.array(0.0))
True                             # np.array_equal itself is blind, confirming the
                                  # general mechanism the brief described
```

## Step 2: what was changed

### `tests/differential/harness.py` -- `_compare_scalar_like`

Added a sign-of-zero guard to the plain-`float` branch, mirroring the
`copysign`-based check the adjacent `complex` branch already used for the
same property. Restricted to `type(np_out) is float` (both sides already
proven same-type by an earlier check in the function) and only engages
when both values are numerically `0.0`, so it cannot touch any
currently-passing non-zero-valued item. Nothing was removed, weakened, or
had tolerance added; this is a strictly additional guard, same shape as
the existing `math.isnan` special-case immediately above it.

### `tests/differential/corpus.py` -- generators

- `binary_corpus()`: added `special/denormal_pair/<f16,f32,f64>`,
  `special/denormal_vs_normal/<f16,f32,f64>`, and
  `special/complex_signed_zero_pair/<c64,c128>` pairs -- denormal
  magnitudes and all-four-sign-combination signed zeros, paired against
  each other and against ordinary values, both real and complex.
- `scalar_operands()`: added signed-zero (`python_float_neg_zero`,
  `numpy_float64_neg_zero`, `numpy_float32_neg_zero`,
  `python_complex_neg_zero`, `numpy_complex128_signed_zero`,
  `zero_d_array_neg_zero`) and denormal (`numpy_float64_denormal`,
  `numpy_float32_denormal`) entries to the scalar right-hand-operand axis.
- `_special_float_values()` (unary corpus, already had real-float
  denormals/signed-zero): added the missing complex counterparts --
  `special/complex_signed_zero/<c64,c128>` (all four sign combinations,
  spelled via `complex(re, im)`, not `-0.0+0j`) and
  `special/complex_denormal/<c64,c128>`.
- `tests/differential/ndarray_float_cases.py`: added `neg_zero`/`pos_zero`
  cases to `ndarray.__float__`'s corpus -- the one item in the suite whose
  result routes DIRECTLY through the fixed `_compare_scalar_like` float
  branch as a plain Python `float`.

### `divmod` -- the one newly-exposed item

```
[FAIL] divmod  (417/418 cases)  -- 1/418 cases failed
    [outer/special/complex_signed_zero_pair/complex128] exception message mismatch (TypeError):
  numpy   : "ufunc 'divmod' not supported for the input types, and the inputs
             could not be safely coerced to any supported types according to
             the casting rule ''safe''"
  anionpy : "ufunc 'floor_divide' not supported for the input types, and the
             inputs could not be safely coerced to any supported types
             according to the casting rule ''safe''"
```

**Mechanism: neither signed-zero nor denormal, despite the triggering
case's name.** Direct reproduction shows this fires for *any* two complex
arrays passed to `np.divmod.outer` / `anionpy.divmod.outer` -- complex is
simply unsupported by `divmod` in real numpy, and anionpy's error message
names the wrong underlying ufunc (`floor_divide`, presumably `divmod`'s own
internal implementation detail leaking into the exception text) instead of
`divmod`. It is a **message-identity defect**, exposed by corpus widening
rather than by either mechanism this ticket set out to test.

**Why it was invisible before, proven by index, not by luck:**
`ufunc_cases.py`'s `.outer()` case builder does not consume
`binary_corpus()` directly -- it samples it via
`ufunc_corpus.sampled(pool, UNARY_SAMPLE_STRIDE)` with
`UNARY_SAMPLE_STRIDE = 12`, i.e. only indices `0, 12, 24, ...` of
`binary_corpus()`'s list are ever exercised through `.outer()`. Before this
ticket, `binary_corpus()` had 26 entries (indices 0-25 -> sampled
`{0, 12, 24}`); `same_shape/complex128` sits at index 10 and was **never
sampled**, so this exact defect existed the entire time and no test could
reach it. Appending 11 new entries (denormal + signed-zero pairs) grew the
list to 37 (indices 0-36 -> sampled `{0, 12, 24, 36}`), and index 36 is
`special/complex_signed_zero_pair/complex128` -- the ticket's own
addition, landing on a sampled index by construction of where it was
appended, not because the underlying defect is actually about signed zero.
**This is filed as its own item below and NOT fixed here.**

## Proof the new corpus additions bite

The `divmod` result above IS the bite-proof for the corpus widening:
before this ticket's `corpus.py` changes (`/tmp/r86base.json`, repo HEAD
`72242f9`), `divmod` passed and the ledger matched the pinned 33-name
baseline exactly. After the widening (`/tmp/r86final.json`), it fails,
attributable by index arithmetic (above) to exactly one added pair. No
other change was made between the two runs besides the corpus/comparator
edits in this ticket.

For the comparator fix specifically (`_compare_scalar_like`'s sign-of-zero
guard), the full suite is silent on its own today -- no currently-declared
`scalar_like=True` item happens to produce a genuine sign-mismatched zero
(confirmed directly for `ndarray.__float__`'s new `neg_zero`/`pos_zero`
cases: anionpy's `__float__` correctly preserves the sign already, so
adding the case did not turn up a bug -- a reassuring answer, reported
honestly rather than discarded). The fix's capability to catch a real
defect is proven at the unit level instead, directly against the live
function, both before and after:

```python
# before this ticket's edit (== fallback):
harness._compare_scalar_like(-0.0, 0.0)  -> (True, '')      # wrong
# after:
harness._compare_scalar_like(-0.0, 0.0)  -> (False, 'value mismatch (sign of zero): ...')  # correct
harness._compare_scalar_like(1.0, 2.0)   -> (False, ...)    # unrelated mismatches still caught
```

## Step 4: newly-exposed false declaration, filed (not fixed)

One item, one mechanism:

### Group: wrong ufunc name in exception message (message-identity, not value)

- **`divmod`** -- `divmod.outer(complex_a, complex_b)` raises `TypeError`
  on both numpy and anionpy (correct: complex genuinely unsupported), but
  anionpy's message says `"ufunc 'floor_divide' not supported..."` where
  numpy's says `"ufunc 'divmod' not supported..."`. Byte-for-byte message
  comparison (this suite's declared standard for exception text, per
  `copyto_cases.py`'s module docstring) correctly fails this. Root cause
  is presumably in whatever internal ufunc anionpy's `divmod`
  implementation delegates to for its unsupported-dtype error path
  (`floor_divide`, going by the leaked name) not substituting its own name
  back in before raising. Not fixed here, per this ticket's mandate.

No signed-zero or denormal defect was newly exposed by this ticket's
corpus widening (the widening did surface a real, previously-unreachable
bug, just not of either family this ticket set out to hunt).
