# TICKET-72: numpy's legacy polynomial API (`poly1d`, `polyval`, `poly`,
# `roots`, `polyfit`, ...) -- 2026-08-08

## Scope

numpy's LEGACY polynomial family -- `poly1d` (class), `poly`, `roots`,
`polyval`, `polyadd`, `polysub`, `polymul`, `polydiv`, `polyder`, `polyint`,
`polyfit`, `convolve`, `array_str`, `correlate` -- the pre-1.4,
highest-degree-first coefficient convention. This is explicitly NOT
`anionpy.polynomial` (the modern chebyshev/legendre/hermite/power-series
package with a lowest-degree-first convention, under concurrent edit by a
different agent in this same tree this session; none of that package's
files were touched here).

Getting to a clean run through the real harness (not just my own probe
scripts) surfaced and fixed three structural mistakes in the corpus file
itself, none of which were about the underlying numeric correctness:

- **Import style.** `poly1d_legacy_cases.py` originally did
  `from tests.differential.registry import ItemSpec` (dotted-package
  style). `registry.py` itself uses bare imports internally
  (`from linalg_cases import ItemSpec`-style), and mixing the two import
  styles makes Python load `registry.py` as two distinct module objects,
  producing a genuine circular-import `ImportError` when the load order
  crosses back through `registry.py -> linalg_cases.py -> registry.py`
  under the dotted name. Fixed by matching the sibling `*_cases.py` files'
  own convention exactly: `import _bootstrap` (repo's own sys.path
  plumbing) then `from registry import ItemSpec` (bare).
- **`epsilon_tolerance` shape and evidence gate.** `ItemSpec.__post_init__`
  requires `epsilon_tolerance` to be a `{dtype_name: (metric, bound)}`
  dict, graded per dtype (a single scalar is explicitly rejected, citing
  the exact same "single item-wide scalar gives every dtype the worst
  dtype's slack" bug the ULP-tolerance path was already hardened against).
  It further requires a matching `epsilon_sweep` entry
  `{dtype_name: (sample_size, measured_value)}` with `sample_size >=
  MIN_ULP_SWEEP_N` (20000) for every declared dtype, and the declared
  bound must equal the measured sweep value exactly (not padded, not
  under-evidenced). My first draft declared a single prose-justified
  `1e-9` scalar with no sweep at all -- this would have been exactly the
  under-evidenced-epsilon defect the repo's own `MIN_ULP_SWEEP_N` gate
  exists to catch. Fixed by writing and running a real independent
  seeded sweep, `/private/tmp/poly_eps_sweep_legacy.py` (seed=9182736,
  N=20000, matching the exact seed/N convention already used for the
  modern `polynomial.polynomial.polyroots`/`polyfit` sweep in
  `polynomial_cases.py`), and declaring the exact measured maxima:
  - `roots` float64 (real-rooted): max abs = `2.7222051279807147e-08`
  - `roots` complex128: max abs = `1.150574417275806e-10`
  - `polyfit` float64: max rel (floor=1.0, matching
    `harness.max_rel_distance`) = `1.963794112607891e-12`

  The `roots` float64 bound is visibly larger than its own complex128
  bound or `polyfit`'s bound for the same reason already documented for
  `polynomial.polynomial.polyroots` in `polynomial_cases.py`: real-rooted
  polynomials built from independently-drawn roots are, for a fraction of
  draws, genuinely ill-conditioned (Wilkinson-polynomial-style root
  sensitivity), so a companion-matrix-entry perturbation on the order of
  1e-13 can move a root by orders of magnitude more than that -- a
  property of root-finding-via-companion-eigenvalues itself, not evidence
  anionpy's `eigvals` is worse.
- **Legacy `roots()` does not sort its output**, and two independent
  eigensolver call paths (real numpy's LAPACK `dgeev` vs anionpy's own
  `linalg.eigvals`) are not guaranteed to return eigenvalues in the same
  order even when every value agrees to near-bit-exactness. Confirmed
  directly: `roots([1, 0, -1])` returns `[1., -1.]` from real numpy but
  `[-1., 1.]` from anionpy -- same two values, swapped order. This would
  have shown up as a spurious FAIL through the real harness (it never did
  through my own probe scripts, which happened to only print/compare
  sorted or single-magnitude cases). Fixed with a `numpy_adapter`/
  `ionp_adapter` pair (`_roots_numpy_sorted`/`_roots_ionp_sorted`) that
  sorts both sides by a rounded `(real, imag)` key before comparison --
  the exact same pattern `chebyshev_cases.py` already uses for
  `chebroots`/`legroots`, reused rather than reinvented.
- **`polyfit`'s return shape depends on its kwargs.** `full=True` returns
  a 5-tuple (coefficients, residuals, rank, singular_values, rcond);
  `cov=True` returns a 2-tuple (coefficients, covariance); with neither
  kwarg it returns a bare coefficient ndarray. Mixing all three shapes
  under one `multi_output=True` spec throws
  `compare_multi_output`'s own "expected numpy to return a tuple, got
  ndarray" guard for the plain cases. Fixed by splitting into three
  specs -- `polyfit` (`multi_output=False`, plain cases only),
  `polyfit_full`, `polyfit_cov` (both `multi_output=True`) -- sharing the
  same `numpy_path`/`ionp_path` and the same measured epsilon (the
  tolerance lives on the returned coefficient array in every variant).

None of these three fixes changed what the underlying Python dispatch code
in `anionpy/_polynomial_legacy.py` does -- they were all corpus-file
correctness fixes, caught precisely because I ran the file through the
real harness instead of stopping at my own hand-rolled probe comparisons.

### Bugs found and fixed in `anionpy/_polynomial_legacy.py` itself

(All found via direct probing before the harness-integration step above;
documented here for completeness.)

- `polyval([], x)`: the empty-`p` case must special-case
  `zeros_like(asarray(x))` in Python (real numpy's own `polyval` never
  enters its multiply-accumulate loop for empty `p`, so `x`'s exact
  dtype/shape passes through unchanged) rather than delegating to the Rust
  kernel, which was returning `float64` where an int64 `x` should stay
  int64.
- `poly()`'s complex-conjugate-pair realification check used
  `iscomplex(a).any()` (anionpy's `iscomplex` means "has nonzero
  imaginary part elementwise", confirmed via its own docstring) instead of
  real numpy's actual check, which is on **dtype**, not elementwise
  values. Fixed to `a.dtype.kind == "c"`. Without the fix,
  `poly([1+1j, 1-1j])` returned `complex128` `[1+0j, -2+0j, 2+0j]` instead
  of the correct `float64` `[1., -2., 2.]`.
- `poly1d.__getitem__` used `self.coeffs.dtype.type(0)`, which doesn't
  exist on anionpy's `dtype` object (`.char`/`.kind` exist, `.type` does
  not, unlike real numpy's). Fixed to
  `asarray(0, dtype=self.coeffs.dtype).item()`.

## Deliberately declined (and why)

Per ticket #45 (`np.convolve`'s summation order is not reproduced against
real numpy's C loop -- verified again this session, unchanged from prior
findings) and ticket #42 (the standing "false exactness declaration"
lesson: a green suite is not evidence, out-of-corpus bit-exactness is):

- **`polymul`** (free function) -- needs `convolve`'s summation order.
- **`convolve`, `correlate`** -- not implemented at all; same reason.
- **`array_str`** -- not implemented (out of scope for this pass; no
  polynomial-specific arithmetic dependency, just not reached).
- **`poly1d.__mul__`/`__rmul__` for non-scalar operands** -- raises
  `NotImplementedError`; scalar multiply IS implemented (pure
  elementwise scale, no convolution). `__pow__` similarly only handles
  `n == 0` and `n == 1`; `n > 1` raises `NotImplementedError` (repeated
  `polymul`).
- **`polyval(p, x)` where `x` is itself a `poly1d`** (polynomial
  composition) -- raises `NotImplementedError`; composition needs
  `polymul` internally in real numpy's own implementation.

Per this ticket's explicit framing: **declining to declare these is the
success condition**, not a shortfall. `poly1d.__truediv__`/`__rtruediv__`
between two `poly1d`s DOES work (uses `polydiv`, which does not depend on
`convolve`'s summation order at all).

## A deliberately unused Rust kernel

`companion_legacy` (in `ionp-core/src/poly_legacy.rs`) is built and unit
tested but **not called** from the final `roots()` implementation. `roots()`
instead assembles the companion matrix in pure Python via
`diag`/`ones`/slice-assignment, matching real numpy's own
`_polynomial_impl.py` line-for-line in structure (it does the same thing
in pure Python internally, then hands the assembled matrix to
`eigvals`). This was a deliberate choice, not dead code: composing from
already-Rust-backed anionpy primitives (`diag`, `ones`, slice assignment)
keeps `roots()`'s pre-eigensolver step trivially auditable against numpy's
own source, and the unused kernel is left in place (tested, not wired) in
case a future session finds a reason to swap it in.

## What was NOT reproducible / measured this session

Nothing from the earlier probe sweeps failed to reproduce when re-run
through the real harness -- the three corpus-file fixes above were format/
evidence-shape corrections surfaced by running through `registry.py`/
`harness.py` for the first time, not numeric disagreements with the
earlier direct-probe results. The one number that changed from an initial
draft is `roots`' bound: the direct-probe sweep in the prior session
segment reported "~1e-14-scale" informally; the real, sweep-gated
measurement this session (seed=9182736, N=20000, run via
`/private/tmp/poly_eps_sweep_legacy.py`) is `2.7222051279807147e-08` for
float64 (real roots) -- three orders of magnitude looser than the earlier
informal estimate, for the ill-conditioning reason explained above (a
handful of degree-6/7 draws with tightly clustered real roots dominate the
max over 20000 samples; small hand-picked corpus cases alone would not
have exposed this). This is the honest number; the informal one from
earlier in the session should be treated as superseded.
