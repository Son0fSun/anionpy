# TICKET-37 — "Add S/U as real dtypes"

Date: 2026-08-08

## True measured population (before building)

`S`/`U` were already fully real in the *type system* before this ticket:
`DType::S(u32)`/`DType::U(u32)` (name/itemsize/promotion/casting) and
`Buffer::S(u32, Vec<Vec<u8>>)`/`Buffer::U(u32, Vec<Vec<u32>>)` (fixed-width,
NUL-padded storage, `zeros`/`ones`/`empty`/`full` support) were already
implemented and verified correct in prior sessions. Measuring live against
this codebase, the actual gap this ticket closed was narrower than "S/U as a
whole": **`anionpy.array()`/`asarray()` could not build an S/U-dtype array
directly from a Python `str`/`bytes` list or tuple** — any such input was
declined with `TypeError: anionpy.array() only supports (possibly nested)
lists/tuples of bool/int/float/complex, or a numpy.ndarray`
(`ndarray_from_pylist_typed`'s catch-all), and an explicit `dtype='U...'`/
`'S...'` target was blocked earlier still, by `dtype_from_pyobj_no_su`'s
explicit `S/U dtypes are not supported here yet` guard in `array_impl`.
Every other numeric-array-construction path in `array_impl` (numpy source,
scalar, `__array__` protocol object) was unaffected and untouched.

Ledger baseline at start of this pass (`tools/coverage.py`): **1335/3091 =
43.19%**, absent 1756 [later remeasured against a fresh suite run at
1714 absent / 42 untested — see "Ledger" section below for why the two
baseline numbers differ and why neither reflects work done under this
ticket]. Suite baseline: **29 failures**, names recorded in
`/private/tmp/suite_before_37.json`.

## What was implemented

`ionp-py/src/lib.rs`:

- Added `all_leaves_str_kind`, `flatten_str_leaves`, `flatten_bytes_leaves`,
  `ndarray_from_pylist_str` — a homogeneous str/bytes Python list/tuple →
  `Buffer::S`/`Buffer::U` construction path, built entirely from Rust logic
  (width computed as max codepoints/bytes across leaves, floored at 1 for
  any non-empty tree; explicit `dtype='U3'`/`'S3'` truncates/pads instead).
  **Zero numpy calls anywhere in this path** — distinct from, and does not
  widen, the grandfathered `char`/`strings` numpy marshalling boundary in
  `ionp-py/src/strings.rs`.
- `array_impl` now computes `target_dtype` via `dtype_from_pyobj` (which
  parses S/U specs) instead of `dtype_from_pyobj_no_su`, with an explicit
  guard immediately after that re-declines every case that isn't a
  list/tuple of the matching str-or-bytes kind — preserving the original
  decline message and behavior for every input this ticket does not cover
  (mixed str+bytes lists, mismatched-kind explicit dtype, empty list with
  explicit S/U dtype, numeric list with S/U dtype target). All ~25 other
  call sites of `dtype_from_pyobj_no_su` elsewhere in the codebase
  (matmul, linalg, reductions, scalars, manip, ndarray_attrs, creation)
  were left untouched — this ticket only touched `array_impl`.

`tests/differential/harness.py`:

- Fixed a real, pre-existing, generically-impacting bug in `_dtype_of()`:
  `np.dtype(d)` on a foreign (non-numpy) dtype-like object duck-types
  through `.name`, which numpy documents/uses only as a *display* string
  for parameterized dtypes (`np.dtype('<U3').name == 'str96'`, and
  `np.dtype('str96')` raises `TypeError` for a **real** numpy dtype too,
  not just anionpy's foreign one). `str(d)` (`'<U3'`/`'|S3'`) is numpy's
  actual reconstructible typestring, so a fallback retry through
  `np.dtype(str(d))` was added before giving up. This only ever *widens*
  successful coercion — it cannot weaken a comparison, and it will matter
  for any future differential test of a real `Buffer::S`/`U`-backed array,
  not just this ticket's cases. Kept as a genuine, narrowly-scoped
  test-infrastructure fix, independent of whatever else lands from this
  ticket.

## What was declined, and why

**A real, adjacent, second gap was discovered and NOT fixed, on purpose.**
While adding differential-corpus cases for the new construction path, the
harness's generic value-comparator needed to materialize a real numpy
array from an anionpy S/U array for comparison — which goes through
`PyArray::__array___no_cast` (`ionp-py/src/lib.rs`, ~line 6655). That
function has a pre-existing, explicit decline:
`Buffer::S(_, _) | Buffer::U(_, _) => Err(PyNotImplementedError::new_err(
"anionpy: __array__ numpy interop for S/U string dtypes is not implemented
yet"))`. This blocks **both** `np.asarray(anionpy_str_array)` real-world
interop **and** the differential harness's own comparison mechanism for
any S/U-dtype result.

Closing it would require adding numpy calls (`numpy.frombuffer`,
`numpy.dtype`, reshape/transpose) at a **new site** in `lib.rs`, outside
`strings.rs`'s already-grandfathered char/strings marshalling boundary.
The ticket's own constraints are explicit: *"must NOT add any NEW numpy
calls anywhere in shipped code"* (with the sole named exception being
input/output marshalling already scoped to `strings.rs`). Implementing
`__array__` for S/U — even though it would be architecturally analogous to
`strings.rs::encode_string_array`'s existing pattern (raw-byte
construction from already-Rust-computed data, numpy used only to receive
output bytes, never to compute a value) — is a **new** call site, and this
ticket's binding rules do not authorize opening one. Rather than stretch
that authorization on my own judgment, I left it alone and am reporting it
as a discovered, real, named follow-on gap:

> `PyArray::__array__`/`__array___no_cast` has no S/U arm. Real numpy
> interop (`np.asarray(anionpy_str_array)`) and `.tolist()`-independent
> comparison of S/U arrays do not work yet. `.tolist()` itself DOES work
> correctly for S/U arrays (verified live) — this is specifically about
> the `__array__`/buffer-protocol path. A related, distinct gap:
> `.astype()` also declines all S/U-involving casts (`"astype involving
> S/U string dtypes is not implemented yet"`, `lib.rs` ~line 5560) — not
> investigated further here, different function, different concern
> (width-changing casts vs. same-buffer interop materialization).

Because of this, the 15 differential-corpus cases originally drafted for
`_array_custom_cases()` (`tests/differential/registry.py`) were **removed
before commit** rather than landed — they cannot pass without the
`__array__` gap being closed first, and landing them as-is would mean
either declaring them prematurely or leaving genuinely new failures in the
suite, both of which the ticket's rules forbid. `registry.py`'s only
surviving change from this ticket is an explanatory comment recording why
those cases are not present. The underlying `array()`/`asarray()`
implementation itself is complete and correct (see out-of-corpus
verification above) — only its representation as a standing regression
test is blocked, by a separate gap this ticket does not have authorization
to close.

Also declined, unchanged from before this ticket (measured, not assumed):
mixed str+bytes list construction (`ip.array(['a', b'b'])` — real numpy
succeeds, promoting to `U`; anionpy declines with a `TypeError`), and an
explicit S/U dtype target paired with a mismatched-kind or non-list-like
source. All still produce the same pre-existing decline text as before
this ticket — a real, acknowledged gap versus numpy, not silently
patched over.
