# Tickets #67 and #69 — zero-extent stride defects (2026-08-08)

Two distinct defects sharing a reproduction case (`shape=(0,3)` etc.).
Re-measured independently against real numpy 2.5.1 rather than trusting
the ticket text. **Both turned out to be real, but not in the shape either
ticket description assumed.**

## Summary

| Ticket | Claim | Verdict |
|---|---|---|
| #67 (Defect A) | `NdArray::from_buffer` (+ ~5 call sites) computes wrong fresh-alloc strides | **Partially real.** `from_buffer` itself, and the ~5 sites the ticket pointed at, are already correct (prior work had fixed them). One call site the ticket did NOT name — `NdArray::reduce_output_layout` / `lift_reduction_keepdims`, the reduction `keepdims=True` re-insertion path — was still wrong. Fixed. |
| #69 (Defect B) | `np.asarray(anionpy_array)` fabricates strides for rank>=2 zero-extent arrays, every dtype | **Real, confirmed**, and worse than stated: it also breaks at **rank 1** for every numeric dtype (the ticket's own table claimed rank 1 was fine — that claim does not reproduce; see "Claims that did not reproduce" below). S/U dtypes happened to dodge it by accident, not by rank. Fixed. |

"fresh-alloc keepdims output whose size is 0," not reductions in general.

## Root cause

**Defect A** — `NdArray::reduce_output_layout` (`ionp-core/src/array.rs`),
used by `lift_reduction_keepdims` to re-insert the reduced axes at
`keepdims=True`, recomputes strides from the generic descending-stride-sort
formula (the "reshape/view" formula) with no size-0 special case of its
own. `from_buffer` and `relayout_by_perm` already carry that special case;
this one function, reachable only through the keepdims-lift path, did not.

**Defect B** — `PyArray::__array___no_cast` (`ionp-py/src/lib.rs`) builds
the exported `numpy.ndarray` via `into_pyarray` (raw wrap of an
already-built Rust `Vec` — does NOT go through numpy's allocator) followed
by `.reshape(permuted_shape)` and `.transpose(inverse_perm)`, both genuine
zero-copy VIEW operations using numpy's "view of an existing buffer" stride
formula, never the "freshly allocated" one. Confirmed live against real
numpy: a *view*/reshape of an already-existing size-0 array does **not**
get zeroed strides (`np.arange(0).reshape(0,3).strides == (24,8)`), only a
genuinely fresh allocation does. `into_pyarray` is neither route numpy
itself uses, so neither of numpy's own rules protects it — it reports
plain itemsize strides for a size-0 buffer at ANY rank. The `Buffer::S`/`Buffer::U`
arms (added in #70, commit 8ece554) happen to dodge this for their own
construction because they round-trip through `numpy.frombuffer(...).copy()`,
and real numpy's `.copy()` DOES apply the fresh-alloc zero rule — an
accident of that specific implementation, not a fix, and it does not help
the 13 numeric arms sharing the same `to_numpy!` macro (confirmed: rank-1
`(0,)` int64 export is also wrong, `(8,)` instead of `(0,)`).

## The fix

**Defect A** (`ionp-core/src/array.rs`, `NdArray::reduce_output_layout`):
after computing the (keepdims or non-keepdims) output `(shape, strides)`
pair, if the output's element count is 0, zero every stride — the same
rule already applied at `from_buffer`/`relayout_by_perm`. Applied
unconditionally (not only inside the `keepdims` arm) so the function is
correct on its own terms regardless of how a future caller sequences it.

**Defect B** (`ionp-py/src/lib.rs`): added a free function
`zero_out_strides_if_empty(py, arr, shape)` that, when `shape`'s product is
0, relabels the already-built numpy container via
`numpy.lib.stride_tricks.as_strided(arr, shape, strides=[0]*ndim)` — a pure
metadata relabel, not a numpy computation (anionpy already decided the
strides should be zero, in Rust, before ever touching numpy; numpy is only
asked to wrap that decision in a container, matching the project's
"numpy hands us containers, never answers" rule). Wired into all three
export arms (`to_numpy!` numeric macro, `Buffer::S`, `Buffer::U`). The
deprecated `arr.strides = ...` direct assignment (numpy 2.4+) was
deliberately avoided — it works but prints a `DeprecationWarning` on every
zero-extent export.

## Regression guards proven to bite

Each fix was reverted in isolation via `patch -R` (not `git checkout`),
rebuilt, and measured — then re-applied via `patch`:

- Reverting the Defect A hunk alone: `zeros((0,3)).sum(axis=1,
  keepdims=True).strides` goes back to `(8, 8)` (wrong) while Defect B's
  export fix still reports `(0, 0)` (correct) — proving the two fixes are
  independent, not accidentally coupled.
- Reverting the Defect B hunk alone: `np.asarray(zeros((0,3))).strides`
  goes back to `(24, 8)` (wrong) while Defect A's keepdims fix still
  reports `(0, 0)` (correct) — same independence proof in the other
  direction.

(These probes used a direct `importlib.util.spec_from_file_location` load
of the compiled `_anionpy.abi3.so`, bypassing `anionpy/__init__.py`, because
another concurrent agent's in-progress, uncommitted edit to
`anionpy/polynomial/_polybase.py` transiently broke the top-level package
import during this session — see "Instrument notes" below. That collision
had cleared by the time of the final full-suite run.)

## Claims from the ticket that did NOT reproduce as stated

- "Rank 1 is fine" (the ticket's own measured table, `(0,) U4` correct) —
  **narrowly true only for that one dtype/family, not in general.** Direct
  measurement here shows rank-1 numeric dtypes (`int64` tried explicitly)
  export as `(8,)` instead of the correct `(0,)` — wrong, at rank 1, before
  this fix. The U4 case in the ticket's table happened to be correct only
  because the S/U export path's zero-width and nonzero-width arms both
  route through numpy constructs (`np.ndarray(shape, dtype)` / `.copy()`)
  that apply numpy's own fresh-alloc zero rule as a side effect — the 13
  numeric arms sharing `to_numpy!` have no equivalent side effect and were
  wrong at every rank >= 1, not just rank >= 2. Repro:
  `np.asarray(anionpy.zeros((0,), dtype='int64')).strides` before this fix
  was `(8,)`, matching neither the ticket's implied "rank 1 is fine" nor
  its own stated `(0,)` baseline for `int64`.

Everything else in the ticket's measured baseline table reproduced exactly
as stated.

## What was NOT changed and why

- `NdArray::from_buffer` itself, `relayout_by_perm`, `ravel_order`, and
  `ionp-py/src/creation.rs`'s `like_strides` (the `zeros_like`/`ones_like`/
  `full_like`/`empty_like` family) were all re-measured and are already
  correct — each already carries an explicit "freshly allocated size-0"
  zero-strides special case, predating this task. No change made to any of
  them; changing correct code would violate the task's own "don't
  manufacture a fix" instruction.
- `reshape`/`reshape_with_order`/`transpose`/`astype`(non-copy path) were
  re-measured and correctly do NOT zero strides for size-0 results, because
  they are genuine views/relabelings of an existing array, not fresh
  allocations — matching real numpy's own view-vs-fresh-alloc distinction
  (`np.arange(0).reshape(0,3).strides == (24,8)`, not `(0,0)`). Leaving
  these alone is deliberate, not an oversight.
- Did not touch `tests/differential/registry.py` or `harness.py` (explicitly
  out of scope — another agent is actively working there) and did not add
  a new corpus case; the direct repro scripts above and this doc are the
  evidence trail instead, per the task's stated preference for standalone
  repro scripts over corpus additions for this task.
