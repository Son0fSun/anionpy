# Ticket #34 — 2026-08-08

Implements and declares the 42-item `*val2d`/`*val3d`/`*valnd`/`*grid2d`/
`*grid3d`/`*vander2d`/`*vander3d` family across all six polynomial bases
(`polynomial`, `chebyshev`, `legendre`, `laguerre`, `hermite`,
`hermite_e`) in `anionpy.polynomial`. Pure-Python only — no Rust changes,
no rebuild required.

**Commit measured against (starting point): `2d8089d`** (working tree
clean before this pass's edits).

## 1. Premise correction

The ticket brief named `_vander_nd`/`_vander_nd_flat` as "the" shared
helper the 42-item family rides on. Reading numpy's real
`polyutils.py` shows this is incomplete: the family actually needs
**four** shared, basis-agnostic private helpers —
`_vander_nd`/`_vander_nd_flat` (vander functions), plus `_valnd`
(val2d/val3d/valnd) and `_gridnd` (grid2d/grid3d) — none of which
existed in `anionpy/polynomial/polyutils.py` before this work. All four
were implemented in `polyutils.py` in the prior session of this ticket,
along with `_nth_slice` and `_prep_points`, which `_valnd`/`_gridnd`
themselves depend on. Every per-basis `<basis>val2d`/`<basis>val3d`/
`<basis>valnd`/`<basis>grid2d`/`<basis>grid3d`/`<basis>vander2d`/
`<basis>vander3d` function is a thin wrapper calling these shared
helpers with its basis's own 1-D `<basis>val` and `<basis>vander`
plugged in — exactly mirroring numpy's own `polynomial.py`/
`chebyshev.py`/etc. wrapper shape.

A prior version of this file's declarations (`anionpy/_state/
polynomial.py`) claimed these 7-per-basis items were "deliberately
time-boxed out" and absent. That claim was wrong on inspection — nothing
about the ticket made them out of scope, and the shared machinery they
need is small and basis-agnostic. That docstring language has been
corrected in place (see `anionpy/_state/polynomial.py`'s module
docstring and the per-basis section comments).

**Committed corpus** (`tests/differential/{polynomial,chebyshev,

**Full suite run** (`tests/differential/run.py --out /tmp/r34_2.json`):
all 42 new items report `"verdict": "pass"`, `"max_ulp": 0.0` — bit-exact

## 5. Scope exclusion: float16/float32/complex64

Not declared, not covered by the new corpus. Root cause is pre-existing
and out of this ticket's scope: the already-shipped, already-declared
1-D `<basis>val`/`<basis>vander` kernels these new functions call
universally upcast float16/float32/complex64 inputs to float64/
complex128 in their Rust implementation — VALUES match numpy bit-exact,
but the returned dtype does not (numpy preserves the narrower dtype
through `val`/`vander`, `nd`-family included). Since every new function
in this ticket is a thin wrapper around those same 1-D kernels, they
inherit the identical divergence. Fixing it means touching the shared
Rust kernel code paths, which is out of this ticket's edit scope (no
Rust files were touched) and would need its own ticket, since it affects
every already-declared 1-D `val`/`vander` item too, not just these 42.
